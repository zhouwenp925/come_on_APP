# 开发与发布指南

## 项目边界与结构

首版根据 PRD 实现 Android MVP，不包含 iOS、账号、云同步、强制阻断、无障碍服务、悬浮窗或商店上架。可安装 APK 是正式交付物；商店审核、厂商实测和推广属于后续发布工作。

| 位置 | 作用 |
|---|---|
| `core/src/main` | 纯 Kotlin 提醒规则、时间计划、事件重建、版本比较 |
| `core/src/test` | 规则去重、时段、时钟、切换、重启等单元测试 |
| `app/src/main/.../ui` | 今天、规则、专注、我的，规则编辑与应用选择 |
| `data` | Room 数据库与显式迁移、DataStore 设置 |
| `platform` | 使用采集、通知、闹钟、守护服务和专注恢复 |
| `update` | GitHub Release 检查、下载恢复、签名校验、安装入口 |
| `app/schemas` | Room 版本快照，必须随迁移提交 |
| `scripts` | Windows 工具链、构建、版本与发版脚本 |
| `.github/workflows` | 推送检查、模拟器验收、签名发版 |

PRD 的“应用使用情况”采用前台事件估算而非宣称与系统数字完全一致。公共 SDK 不暴露真实 Activity instanceId，首版以类名的内部标识辅助区分切换，无法精确区分同类 Activity 的多个实例。手机交互时长是各前台区间的并集，不包含没有已知前台应用的交互。

## 提醒行为

使用规则在采集成功且快照新鲜时评估。连续使用需要守护服务正在运行；娱乐组内切换接续，离开超过或等于 60 秒、锁屏、关屏、关机重启重置，短暂离开时间不累计。每日预算超过阈值后仍需当前使用目标组，未发送时可等下一次有效评估，当天最多一个预算触发。

固定和间隔计划在 Android 10/11 或 Android 12+ 已获 `SCHEDULE_EXACT_ALARM` 特殊访问时使用 `setExactAndAllowWhileIdle`；未授权或调度遇到权限变化时回退到 `setAndAllowWhileIdle`。不申请自动授权的 `USE_EXACT_ALARM`。授权广播及 APP 返回前台时重新安排计划；撤销权限会由系统停止应用并取消精确闹钟，重新打开 APP 后按当前权限恢复。间隔从当天窗口起点锚定，避免漂移。WorkManager 每 15 分钟做维护和恢复；不能保证 15 分钟内准时运行。计划迟到超过 5 分钟丢弃，不补发连串旧提醒。定时回调不查询使用事件，因此不依赖使用访问授权。

文案库保留 `original-g-a` 稳定 ID，新增摘句及独立原创内容。`INSPIRING` 风格选择新励志池，自定义内容及其他风格已收藏的内容仍能出现；屏蔽优先于收藏，近期内容尽量不重复。文案来源、精确定时授权路径与频率限制见 `励志文案与定时提醒.md`。出处链接不在提醒发送时访问，使用记录不会发送给来源站点。

顺序为权限/暂停/安静时段/专注 → 使用有效性 → 去重 → 频率约束 → 文案 → 事务写入待发送 → 系统提交 → 结果记录。数据库唯一键防止重复投递，使用类待发送通知在进程重建后取消，避免以旧状态提醒。通知日志的“已交给系统”不代表用户实际看见。

为降低切换时区、修改时间带来的提醒轰炸，首版同时限制本地自然日和滚动 24 小时的提交数。因此跨日后额度可能尚未完全恢复。稍后提醒绕过普通冷却，但保留静默、每日额度、专注和当前目标组校验；最多两次，连续点击不产生多条待提醒。

## 首次安装

正式 APK 在 `artifacts/shouxin-0.1.1-release.apk`。通过数据线、文件传输或私人分享发送到手机，系统允许这次安装来源后安装。首次安装后打开 APP，完成使用访问和通知，再选择娱乐 APP。为方便实测，把连续提醒阈值临时调低；测试完成恢复 15 分钟。仅使用定时鸡汤时只需通知及可选的闹钟特殊访问。

目前没有服务端，基础功能离线可用。更新检查依赖手机可以访问 GitHub；GitHub 网络不可用时可由发布者分享同签名正式 APK，经 Android 安装器覆盖更新。

## 本地发布新版本

1. 私下备份原签名和配置；在现有工作区修改代码。
2. 运行 `Bump-Version.ps1 -VersionName 0.1.2`，同时递增 `versionCode`（版本必须高于已发布的 0.1.1）。
3. 更新 CHANGELOG；如修改表结构，递增 Room 数据库版本并新增迁移。不得删掉旧迁移，不得启用 destructive fallback。
4. 正式构建，完成自动检查及真机覆盖升级测试。
5. 把源码和版本提交到 main。运行 `Publish-Release.ps1`（GitHub CLI 登录，或 Python 3 + 已有 Git 登录），或进入 GitHub Releases → Draft a new release，标签 `v0.1.2`、目标 main，上传正式 APK 和 SHA-256 文件，作为非预发布版本发布。可先加 `-Draft` 创建草稿；Python 路径支持校验相同草稿附件并继续发布。
6. 旧版 APP → 我的 → 检查更新 → 下载 → 安装更新。若系统要求允许“收心”安装未知应用，用户主动开启后返回，再点击安装。

`Publish-Release.ps1` 核对本地 APK 摘要及远端版本配置，但仍由发布者确保提交内容与 APK 对应。正式 `Build.ps1` 必须成功，不能把 debug APK 改名充当 release。

## 可选 Actions 自动发布

这会把原签名私钥及密码交给 GitHub 加密 Secrets，供发版 runner 使用。源码库中只保存 Secret 名称，不包含实际值。尚未配置时，本地正式构建仍能正常进行。

安装 GitHub CLI，运行 `gh auth login` 并使用有本仓库写权限的账号，然后手动运行：

```powershell
.\scripts\Configure-GitHubSigning.ps1
```

脚本设置四个 Secrets：`SIGNING_KEYSTORE_BASE64`、`SIGNING_STORE_PASSWORD`、`SIGNING_KEY_ALIAS`、`SIGNING_KEY_PASSWORD`，然后设置仓库变量 `SIGNED_RELEASE_CI_ENABLED=true`。未启用时签名工作流跳过，不影响手动本地发版。不要在日志、聊天或普通文件中粘贴实际值。

提交源码和递增版本后：

```powershell
git tag v0.1.2
git push origin main
git push origin v0.1.2
```

标签名必须与 version.properties 一致。`release.yml` 自动检查、签名打包、写 SHA256SUMS 并发布；手动 workflow_dispatch 只生成 signed-release artifact。先有同名 Release 时，工作流不会覆盖附件，需维护者检查后处理。

签名更换、包名更换、versionCode 回退都会导致更新失败。Play App Signing 与本仓库 APK 自签名渠道属于不同发布管理方式，迁移商店之前应专门设计签名与分发策略。

## 验证与后续迭代

自动检查通过后，优先跑 `Android真机验收.md`，记录通知延迟、守护是否持续、锁屏行为、权限撤销和覆盖更新是否保留设置。耗电需要固定亮度、网络、应用操作及守护时长的对照试验，首版不宣称任何耗电指标已经达标。

仪表盘目前展示近 7 日；导出包含保留期内数据。JSON 是阅读/备份输出，没有导入入口。首版迁移测试覆盖添加专注 note 列时原记录不丢失；后续每次实际数据库版本变更都要添加对应的升级测试。

安卓资料：[Room 迁移](https://developer.android.com/training/data-storage/room/migrating-db-versions)、[后台任务](https://developer.android.com/develop/background-work)、[应用签名](https://developer.android.com/studio/publish/app-signing)。
